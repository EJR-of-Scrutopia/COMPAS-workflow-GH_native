# Test assets

`fixture-pieces.json` is a bench.pieces/1 document generated by the UI
repo's own pieces-export test suite (COMPAS-UI-integration-tool,
`.superpowers/sdd/2026-08-20-pieces-export/fixture-pieces.json`), copied
here verbatim. It is real output of the studio's export route
(piece_solids over a tiny bundle plus the bundle's own analysis_mesh),
not hand-authored.

Most recently re-copied 2026-08-20 (Addendum follow-up, closing a
review concern): regenerated at `size=0.6` instead of the route's own
default/test size of `0.9`, because `generators._course_count` is
`max(1, round(mean_radius / size))` and the Tiny contract's mean radius
only clears the "2 courses" threshold below `size ~0.75` -- `0.9`
always cut a single course, which could prove order preservation but
never that Import Pieces' M/K/S trees actually PARTITION by course.
Every size from `0.9` down to `0.15` was probed against the real bundle
route (see the UI repo's `generate_fixture.py` docstring and
`addendum-report.md` for the full table); `0.6` is the cheapest size
that clears 2 courses. `bay_contract` (the studio's other committed
test contract) was checked too and refuses to cut at any size (not
star-shaped about its axis), so `tiny_contract` at a smaller size was
the only option, not a substitution of convenience.

Current shape: 14 pieces, 2 courses, one `base_mesh` (a 3 x 3 grid
surface, 9 vertices, 4 quad faces, unchanged by the size change --
`base_mesh` is the study's analysis mesh, independent of cut size).
Document order and the derived per-course grouping:

- Course 0 (10 pieces): `c0p5, c0p6, c0p7, c0p8, c0p9, c0p0, c0p1, c0p2,
  c0p3, c0p4`
- Course 1 (4 pieces): `c1p2, c1p3, c1p0, c1p1`

Both courses interleave nowhere in the document (all of course 0
precedes all of course 1 here), which is itself informative: the
partitioning check in `Program.cs` groups by `Course` rather than
assuming any particular document-level interleaving, so it holds
regardless of how a future fixture orders its courses.

`Program.cs` reads it to drive `ImportPiecesComponent.ParseDocument`:
piece count, full document-order preservation, vertex/face array
shapes, `base_mesh` shape (Addendum, 2026-08-20), and -- Addendum
follow-up, 2026-08-20 -- the course-tree partitioning contract itself:
parsed `PieceRecord.Course` values (the same field `SolveInstance` keys
`GH_Path(piece.Course)` on) are grouped in document order and asserted
against this fixture's exact per-course counts and in-branch key order,
plus a floor check that at least 2 distinct course values are present
at all. Doctored in memory: the schema/units refusal messages, and a
`base_mesh`-absence tolerance check (the property removed wholesale
from an in-memory copy, proving an export written before the addendum
still parses).

This is the first asset file this harness project has needed; the
convention is a plain `assets/` folder beside `Program.cs`, copied to
the build output (`CopyToOutputDirectory` in
`Ananke.COMPAS.NativeSmoke.csproj`) and resolved at run time relative
to `AppContext.BaseDirectory`, so the check works regardless of the
working directory `dotnet run` is invoked from.
